# Idle Disconnect Follow-up - 13 November 2026

The user reports drops without interaction and authorizes isolated tests only.
No installed app, permission or setting was changed; no real session was stopped.
No new GitHub issue/PR content was read and no release was published.

## Reproduction And Correction

The first common-mode timer correction (9af7331) still depends on the main
thread running. With that thread deliberately blocked for 12 seconds, an
independent pthread using the production Receiver idle watchdog expires after
10 seconds without traffic. Unlike a main-thread watchdog fixture, this observer
continues running while the Sender fixture's main thread is blocked.

TBHeartbeatTimer now owns a DispatchSourceTimer on a dedicated serial queue.
It encodes heartbeats and sends to the captured connection without hopping to
the main actor or reading mutable session state. The connection capture is weak
and fixed to that session, so a delayed tick cannot target a replacement peer.
The heartbeat period remains 2 seconds and the Receiver timeout 10 seconds.

A recursive lock serializes sequence numbering, delivery and cancellation.
Invalidation is idempotent and waits for an already-running send callback;
queued ticks cannot start a new send after it returns. The callback may also
invalidate its own timer. Deinitialization cancels the source.

Received events count successful socket reads, not parsed heartbeat messages.
Final reruns after fixture cleanup again keep all three modes alive (5 reads
each) and the blocked-main case alive (6 reads); the original e90618e method
again expires in tracking and modal modes at approximately 10.02 seconds.
The idle/mode fixture extracts the production startHeartbeat method verbatim,
but substitutes an inert connection and packet encoder. The blocked-main
fixture exercises the actual heartbeat helper, not the complete application.
These are timer/watchdog integration checks, not full NWConnection/capture tests.

The 120-second controls show that inactivity alone does not reproduce the drop
in this setup. A main-thread stall is a demonstrated vulnerability, not evidence
that such a stall actually caused the user's naturally occurring disconnects.
This change cannot prevent physical link loss, process suspension or capture
failure, and is not claimed to fix every intermittent disconnect.
