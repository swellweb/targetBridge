## Reproduced Defect

The production startHeartbeat method uses Timer.scheduledTimer in default mode
and then enqueues its send operation in a MainActor Task. During event-tracking
or modal-panel mode, the default-mode timer does not fire. An idle desktop can
produce no encoded frames, leaving no traffic to satisfy the Receiver's actual
10000 ms idle watchdog. A menu/dialog can therefore cause a false idle expiry.

The fixture extracts the production startHeartbeat method verbatim into an
inert session, sends heartbeat packets over real ephemeral localhost TCP sockets,
and invokes the production Receiver watchdog function. It uses the timeout read
from main.c, no capture, no Bonjour and no connection to the installed Receiver.
It drives the AppKit run-loop modes rather than opening real menus or dialogs.

| Source / Platform | Mode | Sent / Received | Expired |
| --- | --- | --- | --- |
| Original / M3 Pro, macOS 15.5 | tracking | 0 / 0 | Yes, 10.02 s |
| Original / M3 Pro, macOS 15.5 | modal | 0 / 0 | Yes, 10.02 s |
| Fixed / M3 Pro, macOS 15.5 | default | 6 / 6 | No, 12 s |
| Fixed / M3 Pro, macOS 15.5 | tracking | 5 / 5 | No, 12 s |
| Fixed / M3 Pro, macOS 15.5 | modal | 6 / 6 | No, 12 s |
| Fixed / Intel iMac, macOS 14.8.5 | all three | 6 / 6 each | No, 12 s each |

A repeated M3 Pro run again expires both original cases at 10.02 s and keeps
all fixed cases alive with 6 / 6 heartbeats. Startup twice also verifies that
the previous heartbeat timer is invalidated. This demonstrates a genuine defect,
not that every historical disconnect on the user's Macs had this cause.

## Correction And Diagnostics

TBHeartbeatTimer registers the heartbeat in common modes and invokes its
main-actor callback synchronously, avoiding another default-mode UI task.
The 2 s heartbeat period and 10 s Receiver timeout are unchanged. Stop still
invalidates the timer. A main thread blocked entirely can still delay timers.

Sender logs now persist Stop reason, receive EOF/error domain/code, Receiver
teardown and capture-delegate failure. Receiver lifecycle/idle-timeout events
also go to com.targetbridge.receiver / connection at default log level, not
just stderr. Only controlled event names and numeric values are logged there;
no clipboard, key events, frame payloads or desktop contents are recorded.
The new log unit test was observed in the local unified log datastore.
