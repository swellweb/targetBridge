# 3.6.2 Validation - 15 November 2026

Build 20261115000349. Base: v3.6.1, 26c954fd79448ff9fdddfab20bfa7013ec0b5792.
The user requested a verified correction before a stable 3.6.2 publication.
Distribution retains the explicitly discussed ad-hoc/not-notarized limitations;
standard persistent-signing guards are not weakened.

## Correction And Negative Control

The production tb_net_accept function in 3.6.1 requests 8, 6, then 4 MiB.
Version 3.4.2 requested 4 MiB. The patch restores a maximum 4 MiB request,
with 2/1 MiB fallbacks when the larger setting is rejected.
The new native test rejects the 3.6.1 implementation (actual 8388608 bytes),
then passes the patched implementation (4194304 bytes) while checking that
nonblocking, TCP_NODELAY and keepalive remain enabled.

## Isolated Transport Results

check_tcp_latency.rb compiles the actual net.c against tcp_latency_fixture.c.
The fixture uses only ephemeral 127.0.0.1 sockets, no normal app startup,
Bonjour, virtual display, event injection or active-session connection.
It sends 192 frame-sized records at a requested 48 Hz, 312500 bytes normally
and 2000000 every 48 records, with a 4 MiB send buffer and NODELAY. The reader
has a 26 ms processing pause per record plus validation overhead. Backpressure
can reduce the producer rate; this is not a faithful model of every NWConnection
buffer or a real HEVC decoder. Reported age is creation-to-read completion,
not synchronized end-to-end input/display latency.

| Host / policy | p95 age, two runs (ms) | Observed records/s |
| --- | --- | --- |
| ARM / 3.6.1 8 MiB | 932.8, 930.6 | 33.6, 33.1 |
| ARM / 3.4.2 4 MiB | 710.1, 705.7 | 33.9, 33.5 |
| ARM / patched 4 MiB | 712.1, 720.9 | 33.8, 33.4 |
| Intel / 3.6.1 8 MiB | 888.0, 905.0 | 35.5, 35.2 |
| Intel / patched 4 MiB | 667.0, 676.8 | 35.4, 34.9 |

All runs preserve all 192 record sequences and payload bytes (66750000 bytes).
The patched implementation also transfers 192 records with periodic 6000000-byte
records, larger than the receive window, preserving all 82750000 payload bytes.
The observed reduction in this workload is about 23-26%, not a universal latency
guarantee. This identifies a transport queue-budget regression, not the complete
cause or first affected release of issue 237.

## Other Candidates Not Changed

The exact-production frame-pacer probe preserves about 48 fps with ideal 48 Hz
input and alternating 0.5-2 ms jitter, and 47.3 fps with the tested random jitter.
It does not reproduce the reported 38-39 fps. The pacer/capture surface budget
are therefore left unchanged. A missing retry for FFmpeg send EAGAIN was noted,
but the normal decoder path already drains output before the next send; this
was not established as the reported problem and was not patched for this release.
Reference: https://ffmpeg.org/doxygen/7.1/group__lavc__encdec.html
